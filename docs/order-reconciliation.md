# Admin order reconciliation

`POST /admin/orders/:id/reconcile` requires a current catalog administrator. For an online Square order it accepts optional `{ "slantPublicOrderId": "candidate-id" }` to recover a lost draft identity. The API retrieves the candidate and checks its checkout/payment metadata against the paid local order. A client-supplied ID alone grants no authority. Reconciliation never creates a Square payment, requests a refund, creates a Slant draft or processes a manufacturing order.

Each Square online/in-person reconciliation creates an `order_reconciliation_attempts` record before recovery, initially `running`. Completion saves `no_action`, `reported`, `recovered` or `failed` with the starting payment/fulfillment identities, detected issues and observed actions. An interrupted invocation can remain `running`; it does not prove a provider failure or authorize resubmission. A failure to save the initial attempt prevents recovery. Provider and persistence failures during recovery produce a sanitized 502 and a failed attempt when persistence remains available; audit-write failures cannot claim completion.

The response preserves the existing `resultStatus` fulfillment value and adds `attemptId` and `reconciliationStatus`. It also returns `detectedIssues`, `actionsTaken`, `recommendedAction`, current order and local/Slant status. Diagnostic codes include missing Slant identity, paid without confirmed fulfillment, unknown fulfillment outcome, missing/invalid immutable snapshots, stale local status, leftover paid cart lines, and unavailable reconciliation. Reports never include raw provider errors or credentials. Structured logs contain only correlation IDs and diagnostic codes, not customer snapshots.

For an already processed online order, reconciliation retrieves the correlated Slant status and conditionally advances local lifecycle state. Shipped/delivered/canceled state cannot regress to processing, and updates compare the state read before the provider lookup so a concurrent webhook or refund hold wins. Cancellation evidence changes manufacturing state only; it never marks a financial refund. Snapshot-aware finalization removes only the original paid cart lines, preserving subsequent additions or changed configurations. Missing immutable evidence is reported for operator repair instead of manufacturing again.

An in-person sale records a no-op attempt without Slant access or invented customer/shipping requirements. Orders already on refund hold continue through the existing durable [refund operation](square-refunds.md), which retains its own operation/attempt evidence. Reconciliation preserves the existing notification recovery hook; it does not invent webhook evidence or infer shipment email delivery from a status refresh.

Tests use mocked HTTP provider, authentication and Drizzle/D1 boundaries. `test/routes/squareReconciliation.spec.ts` covers mounted authorization, reports, audit reservation/failure, paid-cart comparisons and in-person exclusion. `test/modules/paidOrderReconciliation.spec.ts` checks real reconciliation control flow, provider identity validation, status monotonicity and generated update predicates with scripted database results. They do not prove live D1 concurrency or provider behavior. No schema migration or production operation is required to add this audit path.
