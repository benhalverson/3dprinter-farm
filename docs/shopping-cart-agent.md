# Validated shopping-agent cart tools

Catalog-only runs remain compatible. To enable selection/cart tools, fetch `GET /cart/:cartId/agent-state` with the owning session or `X-Cart-Token`, then include `cart: {id, revision}` in the existing shopping run body. Optional `selection: {productId, quantity, filamentId?}` identifies the current deterministic control selection. Continue sending the separate shopping visit capability in `Authorization: Bearer …`. Cart credentials and verified account identity are forwarded only through trusted internal transport; neither enters model context or durable conversation history.

The model may call `selection_options`, `selection_set`, `cart_add`, `cart_set_quantity`, or `cart_remove`, alongside the existing catalog reads. Options come from the product's fixed material and currently available Slant filaments. Add accepts exact product/filament IDs and bounded integer quantity, derives SKU/material/color on the server, and rechecks availability before writing. Caller/model prices, identities and material overrides are rejected. Ambiguous product/line/color references must be clarified; unavailable or invalid selections cannot mutate a cart. One cart mutation is allowed per run.

Successful tools emit `lulu.cart.v1`, with the usual `runId`/`uiRevision` envelope and a `result`. `status: "selected"` contains a verified `selection` without changing cart contents. `status: "applied"` contains `appliedRevision` and the authoritative `cart: {cartId, revision, items}`. Item prices are current catalog facts, not a checkout quote or charge authorization. Do not infer success from model text or RUN_FINISHED alone.

All direct add/set/remove operations and agent writes share an atomic revision gate. A later direct cart change makes an old run fail without overwriting it. On any newer local selection or direct control action, increment `uiRevision`, cancel the prior run and discard events bearing its old revision. After a direct cart write, fetch fresh agent-state before starting another run. The API checks the cart revision again at the mutation boundary and checks cancellation before committing.

The database stores one action identity per cart/session/run in the same transaction as the change. Replays cannot increment quantity twice. After a lost stream or ambiguous response, use `GET /cart/:cartId/agent-actions/:sessionId/:runId`: 200 returns the applied revision plus current authoritative cart; 404 means no confirmed action at that observation. A still-running original request may complete later, so do not retry an incremental request with a new run ID until its status is terminal and state has been reconciled. Duplicate shopping runs retain their existing terminal/running status behavior and never rerun inference.

Cart ownership/lifetime is independent of the expiring visit. Guest claim rotates the authorization version and revokes in-flight guest access. All recovery reads enforce current ownership and are not cacheable. Budget exhaustion, model errors and cancellation leave deterministic controls available; each tool-loop inference invocation goes through the existing reservation/settlement boundary. This API has no agent payment tool.

Apply generated migration `0033_agent_cart_revisions` after its base migration sequence. It adds cart revision/operation metadata without resetting existing carts. Isolated persistence and HTTP tests exercise actual uniqueness, replay, concurrent adds, stale actions, current ownership, invalid inputs, unavailable filaments and budget failures. Provider inference is mocked, not live certification.
