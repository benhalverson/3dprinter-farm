# Square cancellation and refund recovery

`POST /admin/orders/:id/cancel-refund` requires a current catalog administrator and accepts `{reason?, override?}`. It requests one full refund of the verified Square payment; arbitrary amounts and partial refunds are not accepted. Retain the reason on retries. The response includes `operationId`, `orderId`, `state`, `squareRefundId`, `error`, and `success`. Success is true only for `completed`.

The existing policy remains: shipped/delivered online orders require explicit override. Manufacturing cancellation precedes the refund unless an administrator explicitly overrides its failure. Unknown manufacturing submission must first be reconciled to a known order identity, even with override. In-person sales skip all Slant work.

The operation reserves a durable identity and puts fulfillment on hold before external effects. `cancel_unknown` requires a read of correlated Slant cancellation evidence; retrying does not repeat an uncertain DELETE. An explicit override may release that cancellation hold. Financial states are `unknown`, `pending`, `failed`, or `completed`. Pending is not refunded. A known refund ID is retrieved; an unknown response is recovered by replaying the same immutable full-refund payload and Square idempotency key, never by creating a second key. Square's [RefundPayment](https://developer.squareup.com/reference/square/refunds-api/refund-payment) and [GetPaymentRefund](https://developer.squareup.com/reference/square/refunds-api/get-payment-refund) define these provider operations.

`POST /admin/orders/:id/reconcile` also resumes an order on refund hold, using its saved reason and override. A stable provider failure remains failed and diagnosable; this API does not create a new refund identity to bypass a failed provider decision. Seller/environment changes and mismatched payment/refund evidence are rejected.

Admin history contains deduplicated refund request and outcome events. Existing notification machinery preserves cancellation notifications and queues administrator attention for unknown/failed outcomes when enabled. Cancellation messages do not claim a refund. Customer list/detail adds nullable `refund: {status, amountCents, currency, refundedAt}` from persisted evidence; only completed refunds set `paymentStatus: "refunded"` and `refundedAt`. No credentials, raw provider payloads or administrator reasons enter that customer summary.
