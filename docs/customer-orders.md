# Customer order reads

`GET /orders?limit=20&offset=0` lists the authenticated customer's orders, newest first. Limit is capped at 100. The response is `{accountId, orders, pagination: {limit, offset, count}}`; count is the total matching order count. `GET /orders/:id` returns one owned order. Missing sessions receive 401, missing orders 404, and another customer's order 403. Neither read performs fulfillment or provider calls. Both routes send `Cache-Control: private, no-store`, including authorization failures.

Payment and manufacturing are separate facts. `paymentStatus: "paid"` means verified payment was persisted; it remains paid if manufacturing is delayed or fails. `fulfillmentState` reports the manufacturing stage: `ready` awaits submission, `drafted` has a known draft, `draft_unknown` or `process_unknown` needs reconciliation after an uncertain provider response, `processed` confirms submission, and `drafting`/`processing` denote an in-flight provider request. A rejected submission may return to `ready` while overall `status: "paid_fulfillment_failed"` records the failure. Clients must not suggest paying again because fulfillment is pending or unknown. Overall `status`, `slantStatus`, and tracking describe subsequent production/delivery progress.

Both responses contain safe immutable item snapshots, total/shipping amounts in integer cents, currency, payment and fulfillment states, and available tracking. Item `price` remains a decimal major-currency amount for the existing client contract. Tracking and arrival fields are null when unknown. Internal file and filament IDs, raw provider payloads, customer snapshots and administrator diagnostics are excluded.

`cancellation` is null unless cancellation evidence exists; otherwise it contains `canceledAt`. Cancellation alone never proves a refund. No refund success is inferred from absence of refund evidence. Square refund processing is separate work (#181); consumers must not display a completed refund without an authoritative refund contract.

Each response includes the authenticated `accountId`, including empty lists and detail records. Clients should compare it with their current account before applying a response. Send `X-Expected-Account-Id` to assert the account used to start a request: a mismatch returns 409 `{error: "account_changed"}` before reading orders. The assertion never chooses or authorizes an account; the session remains authoritative. On a mismatch, discard the result and refresh authentication.
